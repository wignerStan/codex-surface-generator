# Codex Code Mode and deferred-tool architecture

Research snapshot: **2026-09-06**.

This note is intentionally separate from [`DESKTOP_ARCHITECTURE.md`](DESKTOP_ARCHITECTURE.md). It documents **model tool mode, per-tool exposure, Code Mode execution, and deferred discovery** in public `openai/codex` source.

Source snapshot used for this note: `openai/codex@52e12e0cb506e7bb2c9e406fc84d922e274a0e40`.

## 1. First distinction: model ToolMode != per-tool ToolExposure

The most important rule is:

```text
ModelInfo.tool_mode = code_mode_only
        !=
ToolExposure::CodeModeOnly for every tool
```

These are different layers.

### Model / turn layer

Public model metadata defines:

```rust
pub enum ToolMode {
    Direct,
    CodeMode,
    CodeModeOnly,
}
```

with snake-case wire values:

```text
direct
code_mode
code_mode_only
```

A current model catalog can therefore advertise:

```json
{
  "tool_mode": "code_mode_only"
}
```

`requested_tool_mode()` uses `model_info.tool_mode` first. Feature flags are only the fallback when the model does not provide a mode:

```text
model_info.tool_mode
    |
    +-- Some(...) -> use model-advertised mode
    |
    `-- None -> CodeModeOnly feature / CodeMode feature / Direct fallback
```

Therefore when a new model advertises `tool_mode: "code_mode_only"`, that is a **model-level routing policy**, not a statement that every registered tool has `ToolExposure::CodeModeOnly`.

## 2. Per-tool exposure has three independent surfaces

Public Codex models tool exposure with three bits:

```text
DIRECT     initial model-visible tool list
DEFERRED   deferred discovery / search surface
CODE_MODE  callable from nested Code Mode JavaScript
```

Conceptually:

```text
ToolExposures = DIRECT | DEFERRED | CODE_MODE
```

The concrete `ToolExposure` enum represents combinations of those bits:

| `ToolExposure` | Direct | Deferred | Code Mode | Meaning |
|---|---:|---:|---:|---|
| `Direct` | yes | no | yes | initially visible and callable from Code Mode |
| `Deferred` | no | yes | yes | lazily discoverable and callable from Code Mode |
| `DeferredModelOnly` | no | yes | no | searchable by model, not callable from nested Code Mode |
| `DirectModelOnly` | yes | no | no | initially visible only, excluded from nested Code Mode |
| `CodeModeOnly` | no | no | yes | nested Code Mode only, not deferred-searchable |
| `Hidden` | no | no | no | registered for dispatch but not model-visible |

This naming is easy to misread. In particular:

```text
ToolExposure::CodeModeOnly
```

means **no Direct and no Deferred surface**. It does **not** mean “a tool used by a model whose ToolMode is CodeModeOnly.”

## 3. What model-level CodeModeOnly changes

For a turn whose effective mode is:

```text
ToolMode::CodeModeOnly
```

Codex builds a Code Mode executor and wait tool:

```text
exec
wait
```

The public Code Mode tool name is `exec`; `wait` resumes a yielded/running cell.

At the same time, `build_model_visible_specs()` removes ordinary Direct tools from the top-level model tool list when those tools are Code-Mode-capable nested tools.

So the intended shape is:

```text
model
  |
  +-- exec        <-- primary execution surface
  +-- wait        <-- continuation for running exec cells
  +-- selected model-only/control tools where applicable
  |
  `-- ordinary code-mode-capable business tools are not exposed as
      independent top-level calls
```

The tool runtimes still exist in the registry. CodeModeOnly primarily changes **how the model reaches them**.

## 4. Code Mode `exec` is not `cua_repl` / `node_repl`

These must remain separate concepts.

### Codex Code Mode

The public `exec` tool is generated by Codex's Code Mode implementation. Its own description says it:

```text
- runs JavaScript in a fresh V8 isolate
- exposes nested tools on the global `tools` object
- has no Node runtime
- has no filesystem access
- has no network access
- has no console
```

So:

```text
Code Mode exec
    = Codex-owned V8-isolate orchestration runtime
```

### `node_repl` / `cua_repl`

`node_repl` and `cua_repl` are special MCP server names recognized by Codex and used for computer/browser-use flows. Current tests associate roughly:

```text
computer-use          -> node_repl
unified-computer-use  -> cua_repl
```

They receive special Guardian / transcript handling.

Therefore:

```text
Code Mode exec != node_repl != cua_repl
```

A REPL-backed MCP tool may itself be reachable through Code Mode like another nested tool, but it is not the runtime that implements Code Mode `exec`.

## 5. Two different deferred-discovery mechanisms

There are two related but distinct discovery paths in current Codex.

### A. Responses / model `tool_search`

Codex has a `ToolSearchHandler` that indexes registered tools whose exposure is deferred:

```text
ToolRegistry
   |
   `-- exposure.is_deferred()
          |
          +-- search_info
          v
     ToolSearchHandler
          |
          | BM25 search
          v
     ToolSearchOutput
          |
          `-- Vec<LoadableToolSpec>
```

This is a model-facing deferred discovery mechanism. The result is a dedicated `ToolSearchOutput`, not ordinary text.

`LoadableToolSpec` carries function/namespace specs suitable for making the discovered tool schema available to the model-facing protocol.

### B. Code Mode deferred nested tools

Code Mode has a separate mechanism.

When `register_code_mode_executors()` walks the registry, it includes every tool for which:

```text
exposure.is_available_in_code_mode() == true
```

That includes `ToolExposure::Deferred`.

For every Code-Mode-capable tool, Codex retains the runtime/spec in:

```text
code_mode_nested_tool_specs
```

including deferred tools.

But it separates prompt/schema presentation:

```text
non-deferred Code Mode tools
    -> enabled_tools
    -> detailed declarations included in the initial exec description

deferred Code Mode tools
    -> omitted from the detailed initial enabled-tools description
    -> runtime is still installed in Code Mode dispatch
    -> metadata remains discoverable through ALL_TOOLS
```

This is the central architecture for model-level CodeModeOnly.

## 6. Deferred discovery inside Code Mode: `ALL_TOOLS`

The Code Mode `exec` description explicitly tells the model:

```text
Some deferred nested tools may be omitted from this description.
They are still available on the global `tools` object and listed in `ALL_TOOLS`.
To find one, filter `ALL_TOOLS` by `name` and `description`.
```

So a CodeModeOnly model can conceptually do:

```javascript
const matches = ALL_TOOLS.filter(
  t => t.name.includes("calendar") ||
       t.description.toLowerCase().includes("event")
);
text(matches);
```

Then, once it knows the normalized tool name, call it through the same Code Mode runtime:

```javascript
const result = await tools.mcp__calendar__create_event({
  /* arguments */
});
text(result);
```

The important point is:

```text
CodeModeOnly deferred discovery
    = discover metadata inside exec via ALL_TOOLS
    + execute via global tools object
```

It is **not necessary to model this as**:

```text
top-level tool_search
    -> dynamically install a tool into the REPL
    -> call it
```

The executable runtime was already registered by Codex. What is deferred is primarily the **model-facing detailed schema/description**, not runtime installation.

## 7. Why deferred tools can still be callable before their full description is shown

`register_code_mode_executors()` keeps two related collections:

```text
code_mode_nested_tool_specs
    = dispatch/runtime set for Code Mode

enabled_tools
    = detailed tools rendered into initial exec instructions
```

A `ToolExposure::Deferred` tool is added to the first collection, but not to the ordinary `enabled_tools` declaration list.

This gives Codex two useful properties:

```text
small initial tool description
+
large callable tool universe
```

The model sees concise metadata through `ALL_TOOLS`, then selects the nested method it needs.

## 8. MCP exposure policy under a CodeModeOnly model

For MCP tools, Codex begins with the server's allowed surfaces and subtracts `omit_tools_from`.

Conceptually:

```text
allowed = {DIRECT, DEFERRED, CODE_MODE} - omitted
```

Then the search policy applies.

Current source contains a CodeModeOnly-specific condition equivalent to:

```text
if tool_search is enabled
and DEFERRED is allowed
and (
    effective model mode != CodeModeOnly
    or CODE_MODE is also allowed
)
then
    remove DIRECT and retain deferred exposure
else
    remove DEFERRED
```

Therefore, under a true model-level CodeModeOnly turn:

> A tool stays on the deferred path only when it is also Code-Mode-capable.

That naturally produces:

```text
DEFERRED + CODE_MODE
        -> ToolExposure::Deferred
```

which means:

```text
not initially exposed as an ordinary top-level business tool
search/discovery metadata retained
nested Code Mode call allowed
```

A pure model-only deferred tool (`DeferredModelOnly`) is not the normal CodeModeOnly business-tool path because it cannot be called from nested Code Mode.

## 9. `omit_tools_from=["deferred"]` under CodeModeOnly

This setting needs model-mode-aware interpretation.

For an MCP server with default support for all three surfaces:

```text
before:
DIRECT + DEFERRED + CODE_MODE
```

applying:

```text
omit_tools_from = ["deferred"]
```

gives approximately:

```text
DIRECT + CODE_MODE
        -> ToolExposure::Direct
```

In a **Direct-mode model**, that means eager top-level model exposure.

In a **CodeModeOnly model**, ordinary Code-Mode-capable Direct tools are hidden from the independent top-level business-tool list and become **eager nested Code Mode tools**: their detailed declarations can be rendered into `exec` rather than being deferred behind `ALL_TOOLS` discovery.

So for a CodeModeOnly model the useful interpretation is:

```text
omit deferred
    != necessarily expose as a separate top-level function

omit deferred
    = do not lazy-discover this tool
      make it part of the eager Code Mode nested tool world
```

This distinction matters for Desktop `codex_app`, which has been observed with `omit_tools_from=["deferred"]` added by Desktop runtime configuration.

See [`DESKTOP_ARCHITECTURE.md`](DESKTOP_ARCHITECTURE.md) for the Desktop-specific MCP bridge.

## 10. `direct_only_tool_namespaces` is a different escape hatch

Codex also has Code Mode configuration that can mark namespaces as direct-only.

For those namespaces the MCP exposure policy removes:

```text
DEFERRED
CODE_MODE
```

leaving Direct-only/model-only exposure.

That maps to:

```text
ToolExposure::DirectModelOnly
```

`DirectModelOnly` deliberately remains a normal model tool even in CodeModeOnly sessions because it is not available through nested Code Mode.

This is how a control-plane tool can remain outside `exec` when required.

## 11. `ToolSpec::ToolSearch` is not a nested Code Mode tool definition

The Code Mode conversion layer supports function, freeform, and namespace tools as nested tool definitions.

It explicitly does not convert:

```text
ToolSpec::ToolSearch
ToolSpec::WebSearch
```

into Code Mode nested definitions.

That is another reason to keep these concepts separate:

```text
Responses tool_search
    = model protocol discovery primitive

ALL_TOOLS + global tools object
    = Code Mode nested discovery/execution world
```

They can coexist in Codex's registry architecture, but they are not the same tool or transport.

## 12. Canonical model for a model-advertised CodeModeOnly turn

```text
                         model metadata
                  tool_mode = code_mode_only
                              |
                              v
                   effective ToolMode
                       CodeModeOnly
                              |
                 +------------+-------------+
                 |                          |
                 v                          v
          model-visible plane         ToolRegistry
                 |                          |
          exec / wait                 tool runtimes
                 |                    + exposure
                 |                          |
                 |                   +------+------+
                 |                   |             |
                 |               eager CM      deferred CM
                 |                   |             |
                 |                   |             +-- omitted from
                 |                   |                 full initial
                 |                   |                 declarations
                 |                   |             +-- listed in ALL_TOOLS
                 |                   |             +-- still callable
                 |                   |                 through tools.*
                 |                   |
                 +---------> fresh V8 isolate
                                 |
                                 +-- global tools object
                                 +-- ALL_TOOLS metadata
                                 +-- store/load helpers
                                 +-- nested tool dispatch
```

This is the concise mental model:

```text
ToolMode::CodeModeOnly
    controls the model/turn execution style.

ToolExposure
    controls where each individual tool can appear.

Deferred + CodeMode
    is the important combination for lazy tools in a CodeModeOnly model.

Code Mode lazy discovery
    happens through ALL_TOOLS metadata inside exec.
```
